# 작성 규칙 (클린룸)

이 저장소의 코드는 **팀 프로젝트 코드를 보고 옮긴 것이 아니라 새로 작성한 것**이어야 합니다. 이력서·포트폴리오에서 "직접 구현"이라고 말할 수 있으려면 아래를 지킵니다.

## 기준 자료

| 쓸 수 있는 것 | 쓰면 안 되는 것 |
| --- | --- |
| [BEHAVIOR-SPEC.md](BEHAVIOR-SPEC.md) — 동작(입력·출력·임계값·안전 규칙)을 **말로** 적은 명세 | 팀 저장소(`aleph-soar-capstone`, `haedam-portal-*`)와 개인 재현판(`haedam-soar`)의 **소스 코드를 복사·번역·거의 같게 다시 쓰기** |
| 공식 문서(FastAPI, SQLAlchemy, React, Graylog, Wazuh, Docker) | 팀원이 작성한 워크플로·규칙·스키마·테스트 코드 |
| 직접 겪고 측정한 사실(시험 결과, 장애 원인) | 팀 문서의 문장 그대로 붙여넣기 |

## 예외: 본인이 작성한 부분 (C 담당)

티켓 저장소(상태 기계·멱등 처리), S7 복구 스크립트는 본인이 작성한 부분입니다. **참고는 가능하지만 새 설계로 다시 작성**하고, 재사용한 부분이 있으면 [PROVENANCE.md](PROVENANCE.md)에 날짜·파일·사유를 적습니다.

## 절차

1. 구현 전에 해당 동작을 BEHAVIOR-SPEC에 말로 적고, **테스트를 먼저** 씁니다.
2. 구현은 명세와 테스트만 보고 합니다. 막히면 공식 문서를 봅니다.
3. 새 모듈을 만들 때 PROVENANCE.md에 "새로 작성 / 본인 이전 작성분 참고"를 한 줄 기록합니다.
4. AI 보조를 사용한 사실은 README에 밝혔고, 생성된 코드는 본인이 이해하고 시험으로 확인한 것만 커밋합니다.

## 이력서에 쓸 때

- "팀 프로젝트(4인)에서 티켓 저장소·S7 복구 담당" 과 "이후 같은 문제를 단독으로 새로 설계·구현(nobugs-soar)"을 **구분해서** 씁니다.
- 팀원이 만든 부분(포털·n8n 워크플로 등)을 본인이 만든 것처럼 쓰지 않습니다.
