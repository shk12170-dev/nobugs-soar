## 긴 버전 (경력 기술서 한 꼭지)

### 공공기관 민원 포털 SOAR — 공격 탐지·자동 대응·자동 원복 시스템 (개인 프로젝트)

**기간** 2026.10 ~ 2026.11 · **역할** 설계·구현 전부(1인) · **형태** 팀 캡스톤을 혼자 PC 한 대에서 새로 설계·재구현

가상 공공기관(해담/누리시청) 민원 포털을 대상으로, **공격 → 탐지 → 자동 대응 → 효과 확인 → 자동 원복**까지
한 사이클을 자동으로 도는 SOAR(보안 오케스트레이션·자동 대응) 시스템을 1인으로 설계·구현했다.

- **6개 공격 시나리오를 실제 서버로 검증**: 로그인 무차별 대입(S1), 계정 탈취 대응(S4·잠금+세션 회수), 웹
  변조 탐지·복구(S7), 스캔+로그인 실패 IP 차단(S8·S10), 서비스 폭주 판정(S12). **6케이스 × 5회 반복 측정에서
  30회 중 29회 자동 대응 확인**(나머지 1회도 측정·구현 결함이 아니라 재알림 묵음 구간 때문임을 티켓 기록으로
  규명). 공격부터 효과 확인까지 **대체로 60초 이내**.
- **대응 엔진을 직접 구현**(Python): 웹훅 수신 → 보호 대상 검사 → 티켓 상태 기계(open→responding→verified→
  restored→closed) → **멱등** 조치 → 반영 확인(차단 목록 재조회) → 효과 확인(실제 403 확인) → **TTL 자동 원복**.
  탐지 규칙이 겹쳐 중복 조치가 나는 문제를 **엔진 직렬화(락)**로 해결.
- **관제 파이프라인 구축**: Graylog·Wazuh·pfSense 로그를 한 곳(Graylog)으로 모으고 이벤트 정의·알림을 직접 작성.
  Docker가 외부 UDP를 컨테이너로 넘기지 못하는 문제를 **호스트 syslog 중계기(UDP 수신 → GELF/TCP 전달)**로
  우회해 pfSense 방화벽 로그를 수집(source `172.16.50.2`로 Graylog 수신 확인).
- **"확인 불가를 성공으로 치지 않는" 검증 원칙**: 효과 확인 프로브는 확인 불가 시 `None`을 반환하고, 모든 문서는
  **확인·부분·미확인**을 구분해 기록. 테스트 주도로 개발하고 실측 중 발견한 결함을 전부 회귀 테스트로 고정.
- **한 번에 재현 가능한 배포**: PowerShell 원클릭 설치 스크립트(venv·프론트 빌드·docker 스택·Graylog 설정·
  중계기 자동 기동), GitHub Actions CI.

**기술 스택** Python(FastAPI), React(Vite), Graylog, Wazuh, pfSense, n8n, Docker Compose, GitHub Actions

## 짧은 버전 (한두 줄)

- 가상 공공기관 민원 포털 SOAR를 1인 설계·구현 — 공격 탐지(Graylog·Wazuh) → 자동 대응(Python 엔진) → 효과
  확인 → 자동 원복. 6개 시나리오를 실제 서버로 검증(6×5회 중 29/30 자동 대응 확인, 대체로 60초 이내).
- 멱등·직렬화·TTL 자동 원복을 갖춘 대응 엔진 직접 구현, Docker UDP 한계를 호스트 syslog 중계기로 우회해
  pfSense 방화벽 로그까지 수집. 테스트 주도 + 원클릭 재현 설치.

## 면접에서 말할 수 있는 포인트

- **중복 대응 문제**: 같은 트래픽에 S8·S10 두 탐지가 동시에 발동해 IP 차단이 중복되던 것을, 엔진의 판단·조치
  구간을 락으로 직렬화하고 조치를 멱등으로 만들어 해결.
- **"에러 없음 ≠ 동작함"**: S7 이벤트가 조용히 안 만들어진 원인(Graylog 필드 계산이 `src_ip`를 필수로 요구)을
  끝까지 추적해 고침. 연동 구간의 데이터 계약을 테스트로 고정.
- **측정 도구도 시험 대상**: 측정 timeout이 Graylog 평가 주기(60초)보다 짧아 오탐이 나던 것을 규명하고 고침.
- **정직한 범위**: 경계 방화벽 차단은 상태만 재현하는 시뮬레이터이고, 엔진이 pfSense를 직접 제어하는 실 IP
  차단은 범위 밖임을 문서에 그대로 밝힘.
