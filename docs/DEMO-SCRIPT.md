# 시연 영상 대본 (한 사이클 녹화용)

공격 → 탐지 → 자동 대응 → (차단·인시던트) → **원복 → 정상 복귀**를 한 번에 보여주는 녹화 대본이다.
화면·조작·내레이션·예상 시간을 장면별로 적었다. 구조는 [ARCHITECTURE.md](ARCHITECTURE.md), 수치는
[MEASUREMENTS.md](MEASUREMENTS.md)를 본다.

## 이 영상이 증명하는 것

1. 공격이 **관제(Graylog·Wazuh)에 탐지**된다.
2. 탐지가 **대응 엔진의 자동 조치**(IP 차단·계정 잠금·파일 복구)로 이어진다.
3. 조치가 **반영·효과까지 확인**된다("확인 불가"를 성공으로 치지 않음).
4. 조치가 **자동으로 원복**되고 서비스가 **정상으로 돌아온다**(원복 절차 존재).

## 실제 타이밍(대본의 전제)

| 구간 | 걸리는 시간 | 근거 |
| --- | --- | --- |
| 공격 재현 → 티켓 생성 | 약 5초 | 제어판 안내 문구 |
| 탐지(Graylog 이벤트 발동) | 최대 ~60초 | Graylog 평가 주기 60초 |
| 조치 → 반영·효과 확인 | 수 초 | 엔진 health 2초 주기 |
| **자동 원복** | 조치 후 **90초** | `release_ttl_seconds=90`(스케줄러 15초 주기로 확인) |

→ S8 한 사이클(공격~원복)은 **대략 2분30초~3분**이다. 녹화를 짧게 하려면 `.env`의
`NB_ENGINE_RELEASE_TTL`을 30 정도로 낮추고 엔진을 다시 띄운다(원복이 조치 후 ~30초로 당겨진다).

---

## 사전 준비 (녹화 전 체크리스트)

- [ ] 스택 기동: `./scripts/setup.ps1 -Live`(S7까지 보일 거면 `-WithWazuh -Live`). **`-Live`가 핵심** —
      안 붙이면 엔진이 모의 실행이라 실제 차단이 안 된다.
- [ ] 포털·대응 API·엔진을 각 터미널에서 실행(설치 마지막 안내 명령), 제어판도 실행:
      `python -m nobugs_tools.panel`
- [ ] 브라우저 탭 5개 준비: 제어판 `:5102` · Graylog `:9100`(로그인해 둠) · 엔진 `:5200` · 포털 `:5100` ·
      (선택) n8n `:5678`
- [ ] Graylog 탭은 미리 `source:172.16.50.2 OR filterlog`나 케이스 검색을 띄워 두고, 시간 범위를 "최근 5분"으로.
- [ ] 제어판에 **오래된 티켓이 많으면** 화면이 지저분하다 — 깨끗한 화면이 필요하면 엔진을 새로 띄워 티켓을 비운다.
- [ ] (원복을 빨리 보여줄 거면) `NB_ENGINE_RELEASE_TTL=30`으로 바꾸고 엔진 재시작.

## 화면 배치 제안

- 메인: **제어판 `:5102`**(공격 버튼 + 티켓 6단계가 한눈에).
- 보조로 전환해 보여줄 탭: Graylog(탐지 증거), 포털(효과 확인), 엔진(티켓 목록/상태).

## 트랙 A — 주 시연: S8 IP 차단 한 사이클 (가볍고 확실, Wazuh 불필요)

> 스캔+로그인 실패를 반복하는 공격이 탐지돼 출발지 IP가 자동 차단되고, 90초 뒤 자동 원복되는 흐름.

### 장면 1 · 평상시 (0:00~0:15)
- **화면**: 포털 `:5100` 첫 화면 → 제어판 `:5102`.
- **내레이션**: "가상 공공기관 민원 포털입니다. 지금은 정상 상태이고, 오른쪽 제어판에서 공격을 재현해 대응
  전 과정을 보겠습니다."

### 장면 2 · 공격 (0:15~0:30)
- **조작**: 제어판에서 **「S8 웹 스캔→로그인」** 버튼 클릭.
- **포인트**: 5초 안에 새 티켓(예: `T-2026...-00xx`, 케이스 `S8`)이 목록 맨 위에 생기고 **① 공격**이 켜진다.
- **내레이션**: "스캔과 로그인 실패를 반복하는 공격입니다. 방금 공격이 재현됐고, 티켓이 열렸습니다."

### 장면 3 · 탐지 (0:30~1:30)
- **화면**: Graylog `:9100` 탭으로 전환, 해당 출발지/케이스 검색(최근 5분).
- **포인트**: 로그인 실패·스캔 로그가 쌓이고 **이벤트가 발동**(Alerts 또는 메시지 수 증가). 제어판으로 돌아오면
  **② 탐지**가 켜져 있다.
- **내레이션**: "로그가 Graylog에 모이고, 직접 작성한 이벤트 정의가 발동합니다. 최대 1분 안에 탐지됩니다."

### 장면 4 · 자동 대응·확인 (1:30~1:50)
- **화면**: 제어판 티켓.
- **포인트**: **③ 조치 → ④ 반영 확인 → ⑤ 효과 확인**이 차례로 켜진다. 포털 `:5100`을 **공격 IP처럼** 접근하면
  차단되어 **403**(효과 확인). (같은 화면에서 보여주기 어려우면 "엔진이 차단 목록을 재조회해 적용을 확인하고,
  차단된 IP가 실제로 403을 받는지까지 확인한다"로 설명.)
- **내레이션**: "엔진이 해당 IP를 차단하고, 차단이 반영됐는지, 실제로 막히는지까지 스스로 확인합니다."

### 장면 5 · 자동 원복·정상 (1:50~3:20)
- **포인트**: 조치 후 **90초**(또는 낮춘 TTL)면 **⑥ 원복**이 켜지고 상태가 `restored`로 바뀐다. 차단이 풀려
  포털이 다시 정상 응답한다.
- **내레이션**: "조치는 영구적이지 않습니다. 설정한 시간이 지나면 엔진이 **자동으로 차단을 풀고**, 서비스가
  정상으로 돌아옵니다. 원복 절차가 설계에 포함돼 있습니다."
- **마무리**: 엔진 `:5200` 티켓 목록을 비춰 `restored` 상태를 보여준다.

## 트랙 B — 변조→복구: S7 (원복을 가장 분명하게, **Wazuh 필요**)

> 웹 루트 파일이 변조되면 Wazuh가 탐지하고, 엔진이 기준본으로 **즉시 복구**한다. TTL을 기다릴 필요가 없어
> 원복을 짧고 확실하게 보여줄 수 있다.

1. **공격**: 제어판 **「S7 홈페이지 변조」** 클릭(또는 web 루트 파일을 직접 바꿔 보여주기). → ① 공격
2. **탐지**: Wazuh 실시간 FIM이 변조를 잡아 Graylog로 보냄(`wazuh_bridge`). → ② 탐지
3. **복구**: 엔진이 기준본으로 파일을 되돌림. → ③ 조치 ④ 반영 ⑤ 효과
4. **정상**: 변조됐던 페이지가 **원래대로** 돌아온 걸 포털에서 보여준다. → ⑥ 원복(`restored`)
- **내레이션**: "변조된 파일을 엔진이 기준본으로 즉시 되돌립니다. 바뀌었던 화면이 원래대로 복구됐습니다."

> 전제: `setup.ps1 -WithWazuh -Live`로 Wazuh 매니저+에이전트가 떠 있어야 한다(무겁다).

## 보조 컷 — n8n 자동 대응 중계 (S1, 30초)

- **조작**: 제어판 **「S1 로그인 무차별 대입」** 클릭.
- **화면**: n8n `:5678` 실행 기록(Executions).
- **포인트**: S1 탐지가 n8n 워크플로로 들어왔다가 그대로 대응 엔진 웹훅으로 넘어간 **실행 기록**이 남는다.
- **내레이션**: "S1은 Graylog에서 n8n을 거쳐 엔진으로 전달됩니다. 자동 대응 흐름이 n8n 실행 기록으로 남습니다."

## 평가 포인트에서 꼭 말할 것

- **보안 3요소와 연결**: 차단·잠금=가용성/기밀성 보호, 변조 복구=무결성 회복.
- **원복 절차**: "조치가 자동으로 풀린다"를 반드시 보여준다(⑥ 원복 + `restored`).
- **정직한 범위**: 경계 차단은 **상태만** 재현하는 시뮬레이터, 엔진의 pfSense 직접 제어(실 IP 차단)는 범위 밖임을
  숨기지 않고 말한다. 대신 pfSense **로그 수집**은 실제로 된다(Graylog에 `filterlog`, source `172.16.50.2`).

## 촬영·재현 팁

- 공격이 **같은 IP로 반복**되면 포털 로그인 횟수 제한(출발지당 5분 20회)에 걸린다 — 제어판 버튼은 매번 다른
  출발지로 재현하니 **버튼을 바로 다시 누르지 말고** 한 사이클이 끝난 뒤 누른다.
- 탐지가 안 뜨면: ① Graylog 시간 범위(최근 5분) ② 엔진이 `-Live`인지 ③ Graylog 이벤트 정의가 올라갔는지
  (`python -m nobugs_tools.graylog setup ... --live`)를 확인한다.
- 티켓이 `verified`에서 안 넘어가면 아직 원복 TTL(90초) 전이다 — 기다리거나 TTL을 낮춘다.
- 전체 흐름 수치는 [MEASUREMENTS.md](MEASUREMENTS.md)의 N=5 측정표로 뒷받침한다(대체로 60초 내 효과 확인).
