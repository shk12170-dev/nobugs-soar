# 반복 측정 결과

`python -m nobugs_tools.measure`로 공격 → 효과 확인(또는 "무해하면 조치 안 함")까지 걸린 시간을 잰다. 회차마다
계정·출발지를 다르게 써서 서로 섞이지 않게 하고, `--salt`(기본은 실행 시각 기준)로 도구를 다시 돌릴 때도 이전
회차와 같은 IP를 또 쓰지 않게 한다 — 같은 IP를 또 쓰면 포털의 로그인 횟수 제한(출발지당 5분에 20회)에 걸려
실제로는 통과할 시도도 429로 막히는 문제를 실제로 겪었다(아래 "시험 중 발견" 참고).

### S7 5회차가 시간 안에 못 끝난 이유(측정 도구 결함 아님)

`measure._s7_round`는 기준본 파일 4개를 돌려 쓴다(`index.html`, `favicon.svg`, 두 자산 파일) — 그래서 N=5의
5회차는 1회차와 같은 파일(`assets/index-DSZvrULP.js`)을 다시 쓴다. 실제 티켓 기록으로 확인한 진행:

- 1회차(06:38:01)가 그 파일을 변조 → 바로 감지·복구(`T-...-0046`, `restored`).
- 5회차(1회차로부터 약 103초 뒤)가 같은 파일을 다시 변조했지만, S7 정의의 재알림 묵음 기간이
  10분(`grace_period_ms`, definitions.py)이라 Graylog가 "같은 키로는 10분 안에 또 알리지 않는다"며
  **알림 자체를 보내지 않았다** — 측정 도구의 90초 시간제한은 당연히 넘겼다.
- 묵음 기간이 끝나는 순간(1회차로부터 정확히 600.0초 뒤인 06:48:01) Graylog가 그제야 알림을 보냈고,
  엔진은 복구가 끝난 이전 티켓을 자동으로 닫은 뒤("자동 종료: 원복 뒤 같은 대상에서 새 탐지가 발생해 새
  사건으로 처리" — `engine.py`) 새 티켓(`T-...-0057`)을 만들어 끝까지 `restored`로 복구했다.

즉 탐지·복구 자체는 결국 정확히 작동했고, 그냥 10분보다 짧은 간격으로 같은 파일을 두 번 재는 측정 설계의
한계였다. S7을 포함해 N≥5로 다시 잴 때는 기준본 파일을 5개 이상으로 늘리거나, 같은 파일을 쓰는 회차 사이에
10분 이상 간격을 두어야 모든 회차가 묵음 기간 없이 측정된다.

## 시험 중 발견·수정한 측정 도구 자체의 결함 3건

1. **시간제한이 Graylog 평가 주기보다 짧았다.** S1·S4·S8·S10은 60초마다 한 번 평가되는데 처음엔 20~30초로
   잡아서, 실제로는 조금만 더 기다리면 성공할 호출이 번갈아 "timeout"으로 보고됐다. 모든 케이스의 기본
   시간제한을 평가 주기보다 넉넉히 길게(90초, S12는 40초) 올렸다.
2. **같은 키를 돌려 쓰는 반복 실행에서 오래된 티켓을 이번 회차 결과로 잘못 집어냈다.** `poll_until`이
   `group_key`와 상태만 보고 찾아서, 도구를 다시 돌리면 이전 실행에서 만들어진(이미 끝난) 티켓을 찾아
   몇 초 만에 "성공"으로 잘못 보고했다. 티켓의 `created_at`이 이번 회차 시작(`since`) 이후인 것만 보도록
   고쳤다(`tests/test_measure.py`에 회귀 테스트).
3. **반복 실행이 서로의 출발지 IP를 밟았다.** 회차 번호만으로 IP를 정하면, 도구를 다시 돌릴 때마다 같은
   IP를 또 써서 포털의 로그인 횟수 제한(출발지당 5분에 20회)에 걸리거나 이전 차단이 남아 있어 공격 자체가
   실패했다(S8에서 `/auth/me` 호출이 깨져 측정 전체가 멈추는 것까지 실제로 겪었다). `--salt`(기본은 실행
   시각 기준)를 IP 대역에 섞어 반복 실행끼리 겹치지 않게 했고, 한 회차가 예외로 터져도 나머지 회차·케이스는
   계속 돌도록 `measure_case`에 회차별 예외 처리를 추가했다.
