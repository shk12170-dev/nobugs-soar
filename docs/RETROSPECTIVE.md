# 회고 (초안)

> 이 문서는 저장소 기록(README·PROVENANCE·MEASUREMENTS)에 이미 적힌 사실만 모아 정리한 초안입니다.
> "느낀 점" 칸은 본인이 직접 채웁니다.

## 무엇을 만들었나

팀 캡스톤(4인, PC 4대)에서 나눠 만든 공공기관 포털 SOAR를 혼자, PC 한 대에서 새로 설계·구현했다.
S1·S4·S7·S8·S10·S12 여섯 케이스가 공격 → 탐지(Graylog·Wazuh) → 자동 대응(n8n·대응 엔진) → 효과 확인 →
원복(자동 또는 사람 확인)까지 돈다. N=5 반복 측정에서 처음엔 30회 중 29회를 확인했고, 남은 1회(S7)의 원인을 찾아 측정 도구를 고친 뒤 다시 재
30회 모두 확인했다.

## 잘된 점

- **명세와 테스트를 먼저 쓴 것.** 실제 서버로 시험하다 찾은 결함을 모두 회귀 테스트로 고정했다.
- **"확인 불가"를 성공으로 치지 않은 것.** 효과 확인 프로브는 확인할 수 없으면 `None`을 돌려주고, 검증 표는
  확인·부분·미확인을 나눠 적었다.
- **안전장치를 기본값으로 둔 것.** 엔진은 기본이 모의 실행이고, S4 잠금은 `zz_` 시험 계정에만, S7 복구는 정해진
  자산 id에만 한다.

## 실제로 겪은 문제와 배운 것

| 문제 | 원인 | 고친 방법 | 배운 것 |
| --- | --- | --- | --- |
| S8·S10 동시 발동으로 `ip_block` 중복 | 같은 트래픽에 두 정의가 동시에 알림 | 엔진 판단·조치 구간을 락으로 직렬화 | 탐지 규칙이 겹치면 대응 쪽에서 멱등·직렬화가 필요하다 |
| S7 이벤트가 조용히 안 만들어짐 | Graylog 필드 계산이 `src_ip`를 필수로 요구 | S7만 `require_values=false` | "에러 없음"이 "동작함"은 아니다. 끝까지 따라가 확인해야 한다 |
| S7 알림이 와도 엔진이 무시 | 웹훅 본문에 `asset_id`·`file_key`가 없음 | 본문에 두 필드 추가 | 연동 구간은 양쪽 데이터 계약을 테스트로 고정해야 한다 |
| 측정이 timeout으로 잘못 보고 | 시간제한이 Graylog 평가 주기(60초)보다 짧음 | 시간제한을 늘림 | 측정 도구도 시험 대상이다 |
| 재실행 때 이전 티켓을 결과로 집음 | `group_key`만으로 검색 | `since` 필터 추가 | |
| 같은 IP 재사용으로 429 | 포털 로그인 횟수 제한 | 실행 시각 기반 `--salt` | |
| 한글 출력 깨짐 | 셸마다 자식 프로세스 콘솔 인코딩이 다름 | 출력을 가로채지 않고 자식이 바로 쓰게 함 | |
| n8n OOM | 512m에서 Node 힙 부족 | 1536m으로 올리고 버전 고정 | |
| pfSense syslog가 안 들어옴 | Docker Desktop(WSL2)이 외부 UDP를 컨테이너로 넘기지 못함 | 호스트 중계기(`syslog_relay`)가 UDP로 받아 GELF/TCP로 전달(원클릭 설치가 자동 기동) | 플랫폼 제약은 우회 경로를 따로 둔다 — source `172.16.50.2`로 Graylog 수신 확인 |

## 아쉬운 점·남은 일

README의 "알려진 한계" 표를 참고한다(엔진 조회 API 인증, 3.12 실측, 새 클론 전체 설치). pfSense 방화벽 로그
수집은 호스트 중계기로 끝냈고(위 표), 엔진이 pfSense를 직접 제어하는 실 IP 차단은 여전히 범위 밖이다.

## 팀 프로젝트와 비교

팀은 대응을 n8n 워크플로로 조립했고, 이 저장소는 대응 로직을 Python 엔진으로 직접 만들었으며 n8n은 S1 중계에만
쓴다. 팀에서 본인이 맡은 부분(티켓 저장소, S7 복구)은 개념만 참고하고 새 설계로 다시 작성했다(PROVENANCE).
