# 단계별 계획

원칙: **테스트 먼저, 단계마다 시연 가능한 결과, 명세에 없는 것은 만들지 않는다.** 스택은 포털 FastAPI + React, 대응 엔진 Python, 관제 Graylog·Wazuh, 실행 docker compose(로컬 한 번에 실행)입니다.

## 전체 흐름

| 단계 | 결과물(시연) | 핵심 검증 |
| --- | --- | --- |
| M0 기반 | 레포·계획·명세·CI 뼈대 | `pytest`가 CI에서 돈다 |
| M1 포털 백엔드 | 가입·로그인·민원·관리자 API | 인증·세션·CSRF·소유권 테스트, 차단 IP 403, 이벤트 기록 |
| M2 포털 프론트 | 시민·담당자·관리자 화면 | 로그인→민원 신청→처리 E2E 1개 |
| M3 이벤트·관제 | 이벤트가 Graylog에 쌓이고 규칙이 발동 | 로그인 실패 10회 → S1 이벤트(스크립트로 재현) |
| M4 대응 엔진 + 티켓 | S1 한 사이클(차단 → 효과 확인 → 자동 원복) | 안전 규칙 단위 테스트, 멱등·교착·시간 초과 대조 |
| M5 케이스 확장 | S4·S8·S10·S12 | 케이스별 시험, S12는 부하 중 차단 |
| M6 Wazuh S7 | 변조 → 복구 | 에이전트 컨테이너, 변조→복구 시험 |
| M7 측정·배포·문서 | 한 번에 실행, 케이스별 N=5 측정 | 설치 스크립트로 처음부터 재현, README 검증 표 |

## 단계 상세

### M0 — 기반 (반나절) ✅ 완료
- 레포·README·CLEANROOM·PROVENANCE·BEHAVIOR-SPEC·PLAN ✅(이 커밋)
- `pyproject`, 디렉터리 구조(`portal/`, `engine/`, `infra/`, `tools/`), GitHub Actions(pytest·린트)
- **완료 조건:** CI 초록, `make test`(또는 스크립트)로 로컬 테스트 실행

### M1 — 포털 백엔드 (FastAPI) ✅ 완료 (테스트 101건)
- 모델: 사용자·세션·민원·민원 이력·차단 IP·로그인 시도·대응 영수증(멱등)
- API: 가입·로그인·로그아웃, 민원 CRUD(소유권), 담당자 배정·상태·답변, 관리자 계정·잠금·비밀번호 재설정
- 미들웨어: 출발지 IP(연결 정보) → 차단 판정 → 세션·CSRF. 404·파일 접근 이벤트
- **대응 API는 별도 앱(별도 포트)** 으로 만들고 일반 앱에는 마운트하지 않는다
- **완료 조건:** 테스트 60개 이상(인증·세션 만료·CSRF·소유권·차단·멱등·분리 포트 404)

### M2 — 포털 프론트 (React + Vite) ✅ 완료 (단위 23 + E2E 7)
- 로그인·가입, 시민 민원 신청·내 민원, 담당자 처리 화면, 관리자 계정 화면
- **완료 조건:** E2E 1개(가입→로그인→민원 신청→담당자 답변→시민 확인), 토큰을 localStorage에 두지 않는다

### M3 — 이벤트·관제 기반 ✅ 완료 (S1 발동 35초, 테스트 17건)
- 이벤트 구조화(JSONL + GELF UDP), compose: Graylog·OpenSearch·MongoDB(메모리 제한·버전 고정), 입력 생성 스크립트
- Graylog 이벤트 정의를 **직접 작성**(S1부터), 알림 연결 스크립트, 공격 재현 스크립트(S1)
- **완료 조건:** 공격 스크립트 실행 → Graylog 이벤트 발동(1분 이내) 화면 캡처

### M4 — 대응 엔진 + 티켓 저장소 (핵심) ✅ 완료 (엔진·도구 테스트 57건, 실제 사이클 10초 차단)
- 엔진(별도 서비스): 웹훅 수신(키 인증) → 보호 대상 검사 → 티켓 열기 → 포털 대응 API 호출(멱등) → 반영 확인(차단 목록 재조회) → 효과 확인 → TTL 자동 원복
- 티켓 저장소: 상태 기계, (케이스, 키)당 열린 티켓 1개, 닫기 사람
- 단위 테스트: 보호 대상, 멱등, **불확실 결과 대조**, **같은 IP 티켓 교착 없음**, dry-run 기본
- **완료 조건:** S1 한 사이클 자동 완주 + 티켓 화면 + 알림 수신함

### M5 — 케이스 확장
- S4(계정 잠금+세션 회수, 사람 복구 절차), S8, S10(경계는 우선 시뮬레이터, 실제 프록시 차단은 별도 과제), S12(헬스체크 3회 판정, 부하 도구, 대응 경로 분리 검증)
- **완료 조건:** 케이스별 실제 모드 1회 완주 + 테스트

### M6 — Wazuh S7
- 에이전트 컨테이너(매니저 버전과 맞춤), 웹 루트 FIM(실시간 + 정기 스캔 보완), 복구 서비스(기준본 복구·격리)
- **완료 조건:** 변조 → 방문자 접근 → S7 이벤트 → 복구 → 효과 확인

### M7 — 측정·배포·문서
- 케이스별 N=5 측정 자동화(회차마다 계정·출발지 분리), 결과 표·그래프
- `setup` 스크립트 + `docker compose up -d`로 **처음부터 재현**, 시작 시 상태 대조
- README 검증 표(확인/부분/미확인 구분), 아키텍처 그림, 스크린샷, 회고, 이력서 갱신
- **완료 조건:** 깨끗한 폴더에서 문서만 보고 설치·시연 성공, 루트 테스트 전부 통과

## 의존 관계와 위험

- M3~M4는 포털(M1)의 이벤트 형식에 의존한다 → 이벤트 필드를 M1 초반에 확정해 BEHAVIOR-SPEC에 반영.
- 디스크·메모리: Graylog+OpenSearch+Wazuh 동시 실행 시 16GB PC에서 디스크 포화를 겪었다 → 개발 중에는 필요한 스택만 켜고 측정 때 전체를 켠다.
- 범위: M1~M4가 핵심이고 M5~M7은 뒤로 갈수록 선택적이다. 일정이 밀리면 S12·S7을 뒤로 미룬다.
- 라이선스·공개: 새 코드는 단독 저작이므로 구현이 정리되면 라이선스를 정하고 공개로 전환한다(그 전까지 비공개).

## 첫 작업 순서 (제안)

1. M0 마무리: 디렉터리·CI·테스트 러너
2. M1 시작: 모델과 인증 테스트부터(테스트 → 구현)
3. 각 단계 끝에 PROVENANCE 갱신, README 상태 갱신, 커밋·푸시
