# 동작 명세 (구현의 기준)

이 문서는 **무엇을 만들지**를 말로 적은 명세입니다. 구현 방법(코드)은 적지 않습니다. 임계값 중 "이전 시험"으로 표시한 값은 팀 프로젝트와 개인 재현에서 실제로 시험해 본 값이며, 새 구현에서도 같은 값으로 시작해 다시 측정합니다.

## 1. 시스템 구성

| 구성 | 역할 |
| --- | --- |
| 포털(웹) | 시민 로그인·가입, 민원 신청·조회, 담당자 처리, 관리자 계정 관리. 모든 요청의 출발지 IP를 **연결 정보에서** 얻는다(전달 헤더를 믿지 않는다) |
| 포털 이벤트 | 요청·로그인 성공/실패·404·파일 접근을 구조화 이벤트로 기록하고 Graylog(GELF)로 보낸다 |
| 탐지(Graylog, Wazuh) | 이벤트를 모아 케이스별 규칙으로 판정하고 대응 엔진을 호출한다. Wazuh는 웹 루트의 파일 변조를 본다 |
| 대응 엔진 | 탐지 알림을 받아 차단·잠금·복구를 수행하고 결과를 티켓에 남긴다. **일반 서비스와 분리된 포트·프로세스**로 동작한다 |
| 티켓 저장소·대시보드 | 사건 단위로 탐지 → 적용 → 효과 확인 → 원복 → 종료를 기록·표시한다 |
| 알림 | 사람이 읽을 수 있는 요약을 알림 채널(로컬 수신함, 선택적으로 Discord)로 보낸다 |

## 2. 포털 동작 요구

- 로그인 실패 5회 이상 같은 계정·IP에서 반복되면 "로그인 실패" 이벤트가 케이스 규칙에 쓰일 수 있도록 **실패 횟수와 시각이 이벤트에 남아야 한다**. 존재하지 않는 계정도 같은 응답·같은 처리 시간을 보인다.
- 세션은 서버 저장, HttpOnly 쿠키, 변경 요청은 CSRF 토큰 필요. 관리자의 잠금·세션 회수가 즉시 반영된다.
- **차단 목록에 있는 IP의 모든 요청은 403(`IP_BLOCKED`)**. 차단 판정이 가장 먼저 일어난다.
- 존재하지 않는 경로는 404 + "웹 스캔" 이벤트. 홈페이지 파일 접근은 파일 키(`index.html`, `assets/...`)와 상태코드를 이벤트에 남긴다.
- **대응 API(차단·해제·잠금)는 별도 포트와 별도 스레드 풀에서만 제공**하고, 일반 포트에서는 404여야 한다(이유: 서비스 포화 시 차단 요청이 늦어지는 것을 시험으로 확인함 — 78초 지연).
- 대응 API는 ① 공용 키 ② 허용 대역 ③ 멱등 키(같은 키·같은 본문은 같은 결과, 다른 본문은 충돌)를 모두 요구한다. 관리자 계정은 자동 대응 대상에서 제외한다.

- (M1에서 확정) 로그인 성공 시 세션을 새로 발급한다(세션 고정 방지). 같은 출발지에서 5분 안에 로그인 실패가 20회 이상이면 429. 담당자는 자기 자신에게만, 관리자는 담당자 누구에게나 민원을 배정할 수 있고, 배정된 담당자(또는 관리자)만 상태 변경·답변을 할 수 있다. 상태는 접수 → 배정 → 처리 중 → 완료 순서로만 바뀌며 낙관적 버전 검사로 동시 변경을 막는다. 남의 민원은 존재 여부도 알 수 없게 404.
- (M1에서 확정) 관리자의 비밀번호 재설정은 잠금 해제·세션 회수를 함께 하며, 탈취 의심 계정(S4)의 **사람 복구 절차**다.
- (M1에서 확정) 일반 포털과 대응 앱을 **같은 DB 파일을 쓰는 두 프로세스**로 띄우며, 동시에 시작해도 표 생성이 실패하지 않아야 한다.

## 3. 케이스별 탐지·대응

| 케이스 | 탐지 조건(이전 시험 값) | 묶는 단위 | 자동 대응 | 원복 |
| --- | --- | --- | --- | --- |
| S1 로그인 무차별 대입 | 같은 계정·IP의 로그인 실패 9회 이상 / 30분 | 계정+IP | 출발지 IP 차단 | 자동(TTL 경과 + 효과 확인) |
| S4 실패 뒤 성공 | 같은 계정·IP의 실패+성공 합 6회 이상, 두 종류 모두 있음 / 10분 | 계정+IP | 계정 잠금 + 세션 전부 회수(시험 계정 `zz_` 접두만 실제 실행) | **사람**(소유자 확인 후 비밀번호 재설정) |
| S8 스캔 후 로그인 | 웹 스캔 + 로그인 실패 두 종류 모두 / 15분 | IP | 출발지 IP 차단 | 자동 |
| S10 3계층 | S8 + 경계 차단 신호 세 종류 / 15분 | IP | 출발지 IP 차단 + 경계 차단 | 자동(경계 → 앱 순서로 해제) |
| S7 홈페이지 변조 | 같은 파일 키에 변조 신호(Wazuh FIM)와 웹 접근 2xx가 모두 / 10분. 기준본 해시와 같은 변경은 제외 | 자산+파일 키 | 기준본으로 복구(기준본에 없는 새 파일은 격리) | 복구 자체가 원복, 사람이 닫음 |
| S12 요청 폭주 | 같은 IP의 요청이 1분에 94건 초과 | IP | **헬스체크 3회가 모두 기준 초과일 때만** 차단(무해한 폭주는 차단 안 함) | 자동 |

## 4. 대응 엔진의 안전 규칙

1. 기본은 모의 실행(dry-run). 실제 조치는 요청에 명시했을 때만.
2. **보호 대상**(정상 사용자 출발지, 관리 대역, 관리자 계정)은 어떤 탐지에도 차단하지 않고 "보호 대상"으로 종료한다.
3. 모든 변경 호출에 멱등 키를 붙이고, 시간 초과 등 불확실한 결과는 자동 재시도하지 않고 **실제 상태를 다시 조회해 대조**한 뒤 티켓에 반영한다.
4. 사건당 열린 티켓은 (케이스, 묶음 키)마다 1개. 같은 IP를 쓰는 티켓이 여럿이어도 원복이 교착되지 않는다(함께 원복 대상이면 서로를 기다리지 않는다).
5. 자동 원복은 TTL 경과 + 효과 확인(공격 출발지 차단 확인) 후에만. S4(계정 잠금)는 자동 해제하지 않는다.
6. 같은 키의 재알림은 일정 시간(grace) 억제된다. 반복 시험은 키(계정·파일)를 바꿔 한다.

## 5. 티켓과 측정

- 상태: `열림 → 대응 중 → 효과 확인 → 원복 → 종료`. 각 조치 줄에 적용 확인·효과 확인·요청/완료 시각을 남긴다. 닫기는 사람이 한다.
- **MTTD**: 조건 충족 → 탐지(티켓 생성). **MTTR**: 조치 완료 → 효과 확인. 정상 사용자 영향은 정상 출발지의 응답 코드·지연 폴링으로 센다(비정상 응답 횟수).
- 케이스마다 5회 반복(회차마다 다른 계정·출발지) 측정을 자동으로 돌려 중앙값·최소·최대를 낸다.

## 6. 비기능

- 한 PC에서 한 번에 설치·실행(Windows 11, 16GB). 비밀값은 무작위 생성하고 저장소에 올리지 않는다. 모든 서비스는 127.0.0.1에만 연다.
- 알림 본문에는 내부 주소·비밀값을 넣지 않는다. 케이스 ID는 한 번만 표기하고 결과는 한국어로 쓴다.
- 환경 문제(디스크 포화, 컨테이너 재시작)에서 상태가 어긋나지 않는다: 시작 시 포털 차단 목록과 티켓을 대조한다.
