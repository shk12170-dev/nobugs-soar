① 팀 프로젝트

경보·기록 PC(C)를 맡았습니다

  • Wazuh: 포털 서버의 경보를 Graylog로 전달. 1,400바이트가 넘는 UDP 경보가 사라지는 문제를 TCP 중계로 해결
  • 보안 대시보드: 티켓 저장소·API·사건 목록과 상세 화면 구현. 조치 성공과 실제 차단 효과를 따로 표시
  • S8 시연: 15분 안에 같은 출발지에서 404와 401이 겹치면 포털 차단. 11/03 성공 회차에서 마지막 입력부터 차단까지 37.9초, 공격자 403·정상 사용자 200 확인
첫 시도: 연결 실패탐지는 됐지만 n8n 웹훅 주소가 등록되지 않아 차단과 티켓으로 이어지지 않았습니다.
수정 후: 끝까지 확인연결을 다시 등록하고 차단·정상 접근·해제까지 확인했습니다. 첫 실패도 숨기지 않고 1/2로 집계했습니다.

팀에서 S7(홈페이지 변조)은 수동 복구 시험까지만 했고, 차단 해제는 사람이 했습니다. 이 빈칸이 개인 재구성의 출발점이 됐습니다.

② 1인 재구성

nobugs-soar

대응 로직을 직접 만든 Python 엔진으로 구현했습니다

포털(FastAPI·React), 대응 엔진(티켓 상태 기계, 같은 요청 중복 처리 방지, 효과 확인, 자동 원복), 탐지 규칙과 복구 로직을 명세만 보고 새로 작성했습니다. 팀은 대응을 n8n 워크플로로 조립했지만, 이 저장소는 엔진이 판단하고 n8n은 Graylog 탐지를 엔진으로 전달하는 자리에 둡니다(S1). Graylog·Wazuh·n8n은 Docker로 띄웁니다.

케이스공격자동 대응실측 (5회)
S1로그인 무차별 대입IP 차단, 시간 지나면 자동 원복5/5
S4로그인 실패 뒤 성공계정 잠금 + 세션 회수, 복구는 사람이 확인5/5
S7홈페이지 변조기준본으로 복구, 새 파일은 격리5/5 (11/12 재측정)
S8스캔 뒤 로그인 시도IP 차단, 자동 원복5/5
S10스캔·로그인·경계 연쇄IP 차단 + 경계 차단(시뮬레이터)5/5
S12요청 폭주서비스가 느려질 때만 조치, 무해하면 조치 없음5/5 (조치 없음이 정답)

11/10 실제 시험에서 S1은 공격 10초 만에 차단과 효과 확인이 끝났고, 30초 뒤 자동 원복됐습니다. S7은 11/10 측정에서 5회 중 1회가 재알림 묵음 기간에 걸려 미확인이었고, 측정 도구를 고쳐 11/12에 다시 5/5로 확인했습니다. 실측값은 모두 개인 PC에서 직접 잰 것이며 팀 PC의 값과 섞지 않았습니다.

문제 해결

  • S8·S10이 같은 트래픽에 동시에 발동: 같은 IP 차단이 중복 기록되는 경쟁 조건을 찾아, 엔진의 판단·조치 구간을 직렬화해 고쳤습니다.
  • S7 이벤트가 조용히 실패: Graylog가 src_ip를 필수로 요구해 변조 신호의 이벤트 생성이 실패했고, 웹훅 본문에 asset_id·file_key가 없어 엔진이 매번 "보호 대상 아님"으로 무시했습니다. 두 가지를 각각 고쳤습니다.
  • 반복 측정 중 429 응답: 같은 IP를 다시 쓰면 포털의 로그인 횟수 제한에 걸려 정상 시도까지 막혔습니다. 회차마다 계정·출발지를 바꾸도록 측정 도구를 고쳤습니다.
  • 새 환경 설치 검증: GitHub에서 새로 받은 폴더에서 설치 스크립트로 처음부터 끝까지 설치해 보고, 막힌 곳을 문서와 스크립트에 반영했습니다.

한계와 다음 과제

  • pfSense는 방화벽 로그를 Graylog로 수집하는 데까지만 확인했고, 엔진이 pfSense를 조작해 IP를 막는 연동은 범위 밖입니다.
  • S10의 경계 차단은 상태만 관리하는 시뮬레이터이며 실제 패킷 차단은 아닙니다.
  • S4와 S7의 마무리는 사람이 확인합니다. 다른 팀과의 공방전은 하지 않았습니다.
  • Python 3.12는 CI로만 확인했고 개발 PC에서는 3.14로 확인했습니다.
